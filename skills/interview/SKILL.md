# 面試題準備

素材建一次，之後每家公司只做客製的那一層。

## Output Contract

- 素材寫 `~/.nextrole/kit/`，單一職缺的產出寫 `~/.nextrole/interviews/<job_id>/qa.md`。

### 誰是真實來源

| 東西 | 真實來源 | 為什麼 |
|---|---|---|
| `kit/`（事實、故事、口徑、弱點） | **本機** | 跨公司共用，不會有人在試算表上改它 |
| 某一家的面試題 `qa.md` | **同步之後改成 Google 那份** | 使用者會在試算表上自己加題目、改答案，那些改動才是最新的 |

⭐ **`qa.md` 一旦同步到試算表，Google 那份就變成準的。** 使用者是在手機上、在通勤時
複習與修改的，那份才反映他真正要講的話。本機的 `qa.md` 從那一刻起是工作副本。

⛔ **所以：要更新某一家的面試題之前，一定要先 `read_sheet_values` 把那個頁籤讀回來**，
把使用者的手改併進去，再寫。直接拿本機的 `qa.md` 重生一份蓋上去，
就是把他自己整理過的東西刪掉 —— 而且他要到面試前才會發現。

- ⚠️ **寫進 Google 試算表前一定要先問過使用者**，並把要寫的內容給他看過。
  他很可能同時在瀏覽器開著那份試算表編輯。
- **只用使用者的真實素材，絕不編造。** 數字、經歷、職稱都不能加工。素材不足就問，不要補洞。
- ⚠️ **動機類的回答一定要跟使用者確認是不是真的。** 這是最容易出錯的地方：
  由事實推論出來的動機聽起來很漂亮，但如果不是他真的想的，他講不出來，現場會露餡。
  寧可誠實說「我一開始是被職務內容吸引的」，也不要編一個他自己不相信的理由。
- **使用者只能講自己真的懂的句子。** 寫給他的稿子如果他看不懂，這份稿子就是廢的。
  凡是用到產業術語或商業模式論述，都要能白話拆解（見「白話解釋名詞」）。

# SOP

判斷使用者要做哪一件事，直接進對應的流程。不確定就問。

| 他要做什麼 | 走哪一段 |
|---|---|
| 第一次用，還沒有素材 | 一、素材建檔 |
| 準備某一家公司 | 二、準備一家公司 |
| 準備好了，想在手機上複習 | 三、同步到 Google 試算表 |
| 面試完了要復盤 | 四、面試後復盤 |
| 問某個名詞是什麼意思 | 白話解釋名詞（隨時） |

一到四是照時間順序的：素材建好 → 準備這一家 → 同步出去 → 面試完回來復盤。
「白話解釋名詞」不在順序上，他隨時問你隨時答。

## 一、素材建檔（第一次跑一次，之後增修）

⭐ **不要照著清單把人問一遍。** 兩條原則：

1. **主履歷已經寫的，不要再問。** 經歷、專案、數字全部先從
   `~/.nextrole/resumes/master-*.md` 抓進來，列給他確認就好。
   問他一題他早就給過答案的問題，是在浪費他的耐心，而且他會開始敷衍。
2. **先模擬題目，再由缺口決定要問什麼。** 問不出重點的原因是照清單問；
   照「這題現在答得出來嗎」問，問到的都是真的缺的東西。

### 先分清楚是哪一種

| 狀況 | 做法 |
|---|---|
| `kit/` 幾乎是空的（第一次用） | **先請他一次給多一點素材**，再用模擬題目補剩下的 |
| `kit/` 已經有東西 | **直接用模擬題目找缺口**，只問答不出來的 |

⛔ **第一次就用模擬題目一題一題問，是錯的做法。** 從零開始的時候缺口是全部，
一題一題問等於用最慢的方式蒐集最基本的資料，他會累到放棄。
先讓他把手上有的東西倒出來，剩下的再靠模擬題目補。

### 步驟

1. READ 讀 `~/.nextrole/kit/` 四份檔案的現況，以及 `~/.nextrole/resumes/master-*.md`。
   有 JD 在手上（從看板來或他貼的）就一起讀，模擬題目會準很多。
2. WRITE **從主履歷把事實庫填好**（`kit/facts.md`）：經歷、專案、數字直接搬進去。
   ⛔ 不要改寫、不要美化、不要補履歷上沒有的東西。
   填完列給他看：「這些是從你履歷抓的，有錯的地方跟我說。」
3. WRITE **第一次用的話，先請他倒素材**（`kit/` 幾乎空的時候）。
   給他一張清單，說明你要什麼、為什麼要，然後**讓他一次給**，不要一題一題問：

   > 「履歷上的我抓好了，但履歷寫不下的東西才是面試會問的。
   >  你手上有什麼就先丟給我，什麼格式都行，一次貼一堆也沒關係：
   >
   >  - **專案的來龍去脈** — 當初為什麼要做、中間出了什麼事、結果怎麼樣
   >  - **數字的口徑** — 履歷上那些數字，各自實際上在算什麼
   >  - **不順利的事** — 做壞的、被推翻的、跟人吵過的。這些是面試最愛問的
   >  - **舊的面試筆記、績效考核、專案報告、週報** — 有什麼丟什麼，我來整理
   >
   >  想不起來也沒關係，等一下我用模擬題目問你，比較好想。」

   收到之後由**你**整理成 `kit/facts.md` 與 `kit/stories.md` 的草稿，列給他確認。
   ⛔ 整理不等於加工：他沒說的不要補，語焉不詳的標「待確認」，不要自己圓成完整的故事。
4. THINK **模擬題目。** 產出他這次會被問到的題目：有 JD 就照 JD 的職責與異常之處出，
   沒有就出通用題（自我介紹、最有成就感的專案、最失敗的一次、跟人衝突、
   為什麼離職、為什麼是我們、你怎麼做決定）。
   逐題自問：**用現在手上的素材，這題答得出來嗎？**
5. WRITE **照模擬面試的順序，一題一題走過去。一題都不要跳過。**
   從第 1 題自我介紹開始，每一題都在它自己的位置上處理：

   - **素材夠的題目** → 當場把答案草稿寫給他看，問「這樣講可以嗎」。
     不是不處理，是不跟他要新素材。
   - **素材不夠的題目** → 在那個位置問他，並說清楚是哪一句追問把這題問空的：

     > 「模擬到一題『你怎麼決定哪條需求先做』，你履歷寫了季度 20 到 30 條需求由你排序，
     >  但沒寫你**根據什麼**排。這題現場一定會被追問。你當時是怎麼決定的？」

   把草稿放在它該出現的位置給他看，比全部做完再一起審好：他當下有前後文，
   看得出這個答案接在上一題後面順不順。等到最後才給，他只會說「都可以」。

   ⚠️ **「素材夠」要看到追問那一層才算。** 履歷上有一行相關的字，不等於這題答得完整。
   每一題都往下追一層再判斷：「所以最後誰決定？」「有沒有你想改、對方不同意的時候？」
   追問就空的，那一題就是缺口。只看第一層會把一半的缺口漏掉。
6. WRITE 缺口通常落在這四類。履歷寫得再好也不會有這些，所以幾乎每次都要問：

   | 類別 | 檔案 | 為什麼履歷寫不出來 |
   |---|---|---|
   | 數字口徑 | `kit/voice.md` | 「20–30 條」是進到清單的還是開發完成的？現場被追問就穿幫 |
   | 故事的張力 | `kit/stories.md` | 履歷是條目。故事要有衝突：誰反對過、資源怎麼不夠、原本以為 A 其實是 B |
   | 不能講的 | `kit/voice.md` | 前公司敏感資訊、面同業要避開的 |
   | 知道但沒實作過 | `kit/voice.md` | 履歷會寫「SQL」，但那是單表查詢還是複雜分析？這種不可 claim |

   薪資（期望帶、底線）也在這裡問，寫進 `kit/voice.md`。
   ⚠️ 註明**底線絕不主動說出口**。
7. WRITE **故事庫**（`kit/stories.md`）照 `rules/故事怎麼寫.md` 寫。
   每個故事照敘事公式：**原本大家以為是 A → 我發現其實是 B → 所以我做了 C → 結果＋數字**。
   ⭐ 先找**張力**。沒有張力的不是故事，是履歷條目，問到沒有張力的就換一個專案問。
   每個故事標一句 🎯 想展現的特質 ＋ Tag，之後換公司才能照特質挑。
   6 到 10 個就夠開始用，不用一次做完。
8. WRITE 建完把四份檔案給他看一遍，**特別是從履歷自動填的那些**，確認沒有寫錯的事實。

### 節奏

到了模擬題目那一段，沿用 `skills/search/rules/技能問卷對話節奏判準.md`：
**一次一題**，不要一次丟五題。

但題數應該遠少於從零問 —— 履歷擋掉一批，第 3 步他自己倒出來的素材又擋掉一批，
剩下真正要問的通常是 5 到 8 題。
**問超過 12 題就代表你在問他已經給過的東西，回頭檢查前兩步有沒有做好。**

⚠️ 第 3 步（請他倒素材）不受「一次一題」限制 —— 那一步就是要他一次給多一點。
一次一題是給模擬題目那一段用的。

## 二、準備一家公司

1. READ 收輸入：JD 全文 ＋ 官網 URL。可選：**面試輪次**（HR／用人主管／創辦人）。
   缺輪次就問 — 輪次決定深淺，不同輪問的東西差很多。
   從看板來的話直接讀 `board.json` 的 `job`，並記住 `job_id`。
2. READ **研究公司。** `WebFetch` 官網、`WebSearch` 近期新聞。
   JS 站抓不到內容時改用 `mcp__Claude_Browser__navigate` ＋ `get_page_text`。
   要抓的是：**產品實際在解什麼問題、目標客群是誰、商業模式、公司階段**。
3. READ 讀 `~/.nextrole/kit/` 的素材。有設定試算表的話，也讀既有的故事庫頁籤。
   **素材是空的（只剩範本骨架）→ 先走「一、素材建檔」**，帶著這份 JD 一起走：
   有 JD 的話模擬題目會準很多，要問的缺口也更少。現在那一段只問履歷答不出來的，
   通常 5 到 8 題就結束，不會把人卡在這裡。
4. THINK ⭐ **找出「這份 JD 的異常之處」。這是最有價值的一步。**
   一般同類職缺不會寫的東西，就是這家公司真正缺的人。
   例：一份 PM 職缺把行銷職責寫進四大職責、又要求設計敏感度 → 推論是「東西做出來了但講不清楚，
   需要會翻譯的人」→ 於是某些看起來像弱點的背景，在那裡反而是賣點。
   **這個推論會決定他整場面試的姿態，比任何單一題目的答案都重要。**
5. WRITE 產出（寫 `~/.nextrole/interviews/<job_id>/qa.md`，格式見 `templates/company-tab.md`）：
   - 公司產品理解（**白話版，他要能自己複述**）
   - 兩到三個關鍵洞察（他講出來會跟其他候選人不一樣的觀點）
   - 客製化自我介紹
   - 預測題 × 故事對照（每題標明用故事庫第幾個，**不要重寫故事內容**）
   - ⭐ 每個主力故事的「所以對你們」收尾句 — **公司專屬，故事庫裡沒有，每家都要現寫**。
     這是產出時最容易漏掉、但差別最大的一項。見 `rules/故事怎麼寫.md`。
   - 缺口題的誠實答法（見 `rules/答題範式.md`）
   - 產品觀察題（早期新創／用人主管面必備）
   - 反問題 3–4 個
   - 薪資提醒
6. WRITE **給使用者審核**，修訂到他滿意。
7. WRITE **問過之後**才同步 Google 試算表（見「三、同步到 Google 試算表」）。
8. WRITE 回報：檔案位置、頁籤連結、今晚該複習什麼。寫回 `board.json` 的 `artifacts.qa`。

## 三、同步到 Google 試算表

本機的 `qa.md` 已經寫好了，這一段是額外的同步，可做可不做。

`config.json` 沒有 `spreadsheet_id`、而且 `sheets_declined` 不是 `true` 時，
**在這裡問**（不要叫他去跑 setup）：

> 「要把這份面試題同步到 Google 試算表嗎？（手機上就看得到，複習比較方便）」
> - 已經有一份 → 請他貼網址，從 `/spreadsheets/d/<ID>/` 取出 ID 寫進 `config.json`
> - 還沒有 → 用 `mcp__google_workspace__create_spreadsheet` 建一份，標題讓他決定
> - 不用 → 就到這裡結束，本機檔案已經夠用。把 `config.json` 的
>   `sheets_declined` 設成 `true`，**之後不要再問第二次**

他手上剛好有一份剛產出的面試題，這時候才判斷得出來要不要同步。

1. READ 讀 `rules/試算表格式規範.md`。
2. READ ⭐ **先 `read_sheet_values` 把這家的頁籤讀回來**（不是第一次同步的話）。
   試算表那份是準的 —— 他會在手機上加題目、改答案。**先讀回來、把他的手改併進去，
   再寫回去。** 跳過這一步就是把他自己整理過的東西刪掉，而且他要到面試前才會發現。
3. WRITE 有衝突就講出來，讓他決定：

   > 「試算表上第 4 題你自己改過答案，我這次產出的是另一個版本。
   >  要留你的、留我的、還是我把兩邊併起來？」

   ⛔ 不要自己合併掉。他手改過的那一句，通常有你不知道的理由。
4. WRITE **把要寫的內容給使用者看，問他可不可以寫。** 這一步不可省。
5. WRITE `create_sheet`（新公司）＋ `modify_sheet_values` 寫入。
6. WRITE `format_sheet_range` 套格式。**`WRAP` ＋ `TOP` 不可省**，不套的話長文字會擠成一行看不到。
7. WRITE 回報頁籤連結，寫回 `board.json` 的 `artifacts.sheet_tab`。
8. WRITE 同步完把本機的 `qa.md` 也更新成同一份內容，兩邊不要各說各話。
   之後以試算表為準（見 Output Contract）。

⚠️ Google 工具回報需要授權時，把授權連結**原樣**貼給使用者點，不要自己想辦法繞過。

## 四、面試後復盤

1. READ 讀 `~/.nextrole/interviews/<job_id>/qa.md` 的現況。
2. WRITE 問：被問到哪些**意外題**？當場怎麼答的？哪裡答得心虛？
3. WRITE 把每個答不好的題目**包裝成故事**。條列式的重點沒有用 — 上場講不出來。
4. THINK 判斷這題是**通用**還是**這家專屬**：
   - 通用 → 補進 `kit/stories.md` 或試算表的常見問題頁籤
   - 專屬 → 寫進 `qa.md` 的復盤區，加分隔列 `— 復盤 YYYY/MM/DD —`
5. WRITE 產生了新的可重用故事就加進 `kit/stories.md`。
6. WRITE 順手問要不要更新看板狀態。

## 白話解釋名詞（隨時可以插進來）

使用者會問「MRD 是什麼」「ROI 怎麼算」「Lean Canvas 解釋一下」。
**這不是離題，這是面試準備的一部分** — 他要能在面試中自然講出這些詞，前提是真的懂。

1. **一句話定義**（不要用另一個術語解釋術語）
2. **白話展開** — 用對比表，或用他熟悉的東西類比
3. **跟這家公司的關係** — 為什麼這個詞會在這場面試出現
4. ⭐ **他的經驗裡對應到什麼** — 從 `kit/facts.md` 找他實際做過的事接上去
5. **面試可以怎麼講** — 給一段可直接說的話

第 4 點最重要。**把新名詞接回他已經做過的事，他才記得住也講得出來。**

## 產出風格

中文、口語、**可以直接照唸的腳本**，不是條列大綱。語氣往前看不抱怨。
高風險題要同時講「講什麼」和「別講什麼」。

發現使用者的說法有問題（數字錯、口徑不一致、邏輯硬拗）要**當場指出**，不要順著寫下去。

## 已知地雷

- `cd ~/.nextrole/bin` 失敗時（通常是 plugin 更新過，symlink 指向舊版本），跑一次 `/nextrole:setup` 就會重新指好。
- ⚠️ 素材裡出現「我們曾經遇到」「過去專案中」這類說法時，**先問他是真是假**。
  情境題的假設很容易在轉寫時變成經歷，對方一追問就穿幫。
- ⚠️ 不要幫使用者引用他沒讀過的研究或報告。同樣的洞察用他自己的話講。
- ⚠️ 他沒實作過的東西不可 claim。要提就標明「我看過有人這樣做，我還沒實作」。
